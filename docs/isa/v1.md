# The nocompiler profile, version 1

Nov 20, 2026. English rendering of the v1 specification draft (the original,
in Japanese, is the authority where the two differ), with the decisions on
its open items at the end. Measured results of the acceptance criteria are in
[v1-results.md](v1-results.md).

## Summary

v1 keeps the v0 rules R1 to R5 and adds a frame rule R6, a structured form,
four theorems that follow from the checks, and relocatable proof units. The
aim is one claim, backed by measurement: not only "RISC-V that is easy to
trust" but "RISC-V that is easy to prove".

| | v0 (now) | v1 (this spec) |
| --- | --- | --- |
| Rules | R1 to R5; Lean checks R1 to R3 | R1 to R6; Lean checks all |
| Theorems from the checks | `Struct.cfi` (control) | plus soundness of the structured semantics, non-interference of slots, ABI preservation, stack bound |
| Automated proof covers | calls, syscalls, leaf functions without a frame | every function at level L2 |
| Unit of proof | an ELF at fixed addresses | a relocatable function; the placement is an argument of the theorem |
| How code is written | C through clang | the structured form; clang's output lowers to the same form |
| Cut points | loop heads only | loop heads (required) and block ends (optional) |
| Trusted base | the table in `trust.md` | unchanged |

The rules were checked against the shape of clang 18.1.3 output: all 21
functions of the repository's corpus fit R6, and 24 of 26 further functions
written for the purpose. The two that did not were a variable-length array
and a function taking more than eight arguments. Only the shapes 6a to 6d
were examined; neither the 6e check nor the checker was implemented then.

## Decisions revised during review

| Said before | After review | Why |
| --- | --- | --- |
| R4/R5 in Lean make `Preserved` free | Free inside a proof; nothing is said about functions without one | With the stack in memory, "no other store clobbers the frame" is a premise; it comes from the permission discipline every function proof already shows |
| Never copy `sp`; put address-taken variables on a separate stack | Split one frame into *slots* and *address-taken ranges* | No second stack, no reserved register; clang's output already has this shape |
| Define a new WASM-like IR | No new language: the block/loop tree with profile instructions as leaves is the structured program | `Struct.Func` is nearly that already; the bytes map one-to-one |
| Generate a per-function lifting theorem from bytes to IR | Prove soundness once; per function only the checker's evaluation | `<name>_checked` already comes from kernel evaluation; no per-function proof terms |
| Parametrise proofs by a base address | Make the unit of proof "bytes plus relocations" | Distances to callees and data are embedded in instruction words; a base alone does not suffice |
| Put value typing (i32/i64) in the checker | Not a rule; handled by lemmas and the normal form | That W instructions produce sign-extended results follows from their semantics unconditionally |
| Linear-memory confinement (base + 32-bit index) | Not included | It changes how pointers are passed, breaks linking with ordinary programs, and conflicts with "not a sandbox" in the ROADMAP |

R3 stays in v1: nesting by address is what makes the bytes and the
structured form correspond one-to-one. It costs nothing when an LLM writes
the code directly; the cost on the clang side (`-disable-block-placement`) is
to be removed by LLVM support.

"The kernel exceeded 9 GB at 160 instructions" is history; `Auto.lean` records
the rules that avoid it. The checking cost at hundreds of instructions is
still unmeasured.

## Design principles

1. **Claims are about machine code; proofs are on the structure.** A theorem
   is always about the bytes and the machine (`HwStep`). The structured form,
   the checker and the tactics are proof tools and are not trusted.
2. **A rule comes with a theorem.** A rule is added only when a theorem that
   holds for every function satisfying it can be proved once. No rule without
   a theorem.
3. **Rules are per function and graded.** A function outside the rules can
   still be proved; it loses only automation.
4. **The binary stays a binary.** It runs unchanged on ordinary RV64, keeps
   the LP64 calling convention, and nothing is enforced at load time.
5. **One form.** What the LLM writes, what `disasm` prints and what a proof
   walks is the same structured form.
6. **No addresses in proofs.** Proofs are about relocatable functions; the
   placement is an argument of the theorem.
7. **Every claim is measured.** Where there is an external oracle, compare
   with it; proofs get negative controls (the proof fails on a broken binary).

## Conformance levels

Three levels per function; a binary's level is the minimum over its functions.

| Level | Rules | What the checks give | Left to prove per function |
| --- | --- | --- | --- |
| L0 | R1 (decode) | nothing | everything, by hand with the `Reach` rules |
| L1 structured | R1 to R3 | consistent control (`Struct.cfi`); proofs may use the structured semantics (T1) | invariants, measures, postconditions, frame reads and writes, register preservation |
| L2 frame | R1 to R6 | also slot non-interference (T2), ABI preservation (T3), stack bound (T4) | invariants, measures, postconditions |

L0/L1 functions are proved with the same `Verified` and can be called from L2
functions through their spec alone.

## Rules

R1 to R3 and R5 are as in v0; R4 is narrowed in one place; R6 is new. The
instruction subset (RV64IM + Zba + Zbb), alignment and jump-target
restrictions, and the LP64 calling convention are unchanged.

| Rule | Content | Change from v0 |
| --- | --- | --- |
| R1 decode | Every word decodes to a profile instruction | none |
| R2 control | Control goes only to the next instruction, a branch target in the function, a call or tail call to a function entry, or a return by `jalr zero, 0(ra)` | none |
| R3 structure | A branch target is the end of an enclosing block or the head of an enclosing loop | none |
| R4 registers | `gp` and `tp` are never written. `ra` is written only by calls and by an `ld` from its save slot | "a reload from the stack" narrowed to "from `ra`'s save slot" |
| R5 stack | `sp` is written only by `addi sp, sp, k` (k a multiple of 16). Its offset from the entry is unique at each instruction and 0 at returns and tail calls | none |
| R6 frame | below | new |

R4 to R6 are checked in Lean as well as in Rust, and `<name>_checked` states
the level reached.

### R6 frame

A function's frame is the `frame` bytes below the entry `sp` (the maximum
depth R5 determines).

- **6a Uses of `sp`.** `sp` appears as an operand in three forms only:
  `addi sp, sp, k`; as the base of a load or store; `addi rd, sp, k` with
  `rd` not `sp`. The value of `sp` is never stored to memory or used in any
  other operation.
- **6b Partition of the frame.** Every byte of the frame belongs, by the
  metadata, to one of: a **slot** (8 bytes, 8-aligned), an **address-taken
  range** (any length), or unused.
- **6c `sp`-based accesses.** A slot is touched only by an `ld` or `sd` at
  exactly its offset. An address-taken range may be touched with any width,
  provided the access lies within one range. Nothing outside the function's
  own frame is touched `sp`-based.
- **6d Taking addresses.** The address made by `addi rd, sp, k` is inside an
  address-taken range or at its end.
- **6e Saving.** Every callee-saved register the function writes, and `ra` in
  a function that calls, has exactly one save slot. At every return and tail
  call those registers hold their entry values again. The check is a dataflow
  along the tree tracking "register r holds its entry value" and "slot k holds
  the entry value of r".

Slots correspond to WebAssembly locals: they have no address and are touched
only by statically known instructions. Address-taken ranges are ordinary
memory, owned by the function, in its permissions, and may be passed to
callees.

A wrong partition does not break soundness; proofs just stop going through.

### Outside L2

- More than eight arguments (passed on the stack). The receiver violates 6c.
  The caller fits the shape, but an L2 proof does not go through. Variadic
  arguments fit the shape as far as they are passed in registers (the save
  area becomes an address-taken range).
- Frame pointers (violate 6d; need `-fomit-frame-pointer`, the default at
  `-O2`).
- `alloca` and variable-length arrays (already outside v0's R5).

### Against clang's output (clang 18.1.3, `nocompiler cc` flags plus `-O2`)

- `sp` appeared only in the three forms of 6a (except with variable-length
  arrays).
- Saves and spills are all 8-byte `ld`/`sd`, even for 32-bit values (checked
  on a function with 22 slots): the reason slots are fixed at 8 bytes.
- An address-taken variable is read `sp`-based directly after a call, as in
  `lw a0, 8(sp)`: the reason 6c allows direct accesses to a range.
- A range's length cannot be determined from the code. In the structured form
  the writer declares it; for clang's output `annotate` estimates it (decision
  5 below).

## The structured form

A block/loop tree with the profile's instructions as leaves, one-to-one with
the bytes. The form the LLM writes, `disasm` prints and proofs walk. Trusted:
the Lean kernel, the machine and environment model, and the text of the specs;
the audit matches the ELF with the bytes the proofs are about.

### Statements

| Statement | Machine code | Notes |
| --- | --- | --- |
| an ordinary instruction (arithmetic, load, store, `ecall`) | 1 word | the profile instruction as is |
| `block $l` ... `end`, `loop $l` ... `end` | none | tree nodes; a label is visible only inside its node |
| `beq a, b, $l` and the other branches, `j $l` | 1 word | a block's label means its end, a loop's its head |
| `call f` | 2 words (`auipc ra`, `jalr ra`) | by symbol |
| `tail f` | 2 words (`auipc t1`, `jalr zero`) | tail call |
| `ret` | 1 word (`jalr zero, 0(ra)`) | |
| `auipc rd, %pcrel_hi(sym)` | 1 word | upper part of a data address, pc-relative |
| an instruction with immediate `%pcrel_lo(...)` (`addi`, loads, stores) | 1 word | adds the lower part; several instructions may use one `auipc` |

- **Every statement has a fixed number of words.** Pseudo-instructions whose
  expansion depends on the value, like `li`, are not included.
- **Branch targets are labels.** Only labels of enclosing nodes can be
  referred to, so R3 holds by construction. Names, not depth numbers.

### Example

```
func sum
  addi a2, zero, 0
  block $done
    beq  a1, zero, $done
    loop $next
      ld   a3, 0(a0)
      add  a2, a3, a2
      addi a1, a1, -1
      addi a0, a0, 8
      bne  a1, zero, $next
    end
  end
  addi a0, a2, 0
  ret

func sum2
  frame 32
    slot 24 save ra
    slot 16 save s0
    slot  8 save s1
    slot  0 save s2
  addi sp, sp, -32
  sd   ra, 24(sp)
  sd   s0, 16(sp)
  sd   s1, 8(sp)
  sd   s2, 0(sp)
  addi s0, a3, 0
  addi s1, a2, 0
  call sum
  addi s2, a0, 0
  addi a0, s1, 0
  addi a1, s0, 0
  call sum
  add  a0, a0, s2
  ld   ra, 24(sp)
  ld   s0, 16(sp)
  ld   s1, 8(sp)
  ld   s2, 0(sp)
  addi sp, sp, 32
  ret
```

The declarations under `frame` are R6's partition. Offsets count from the
bottom of the frame; three kinds: `slot k save r`, `slot k spill`, and
`mem k len` (an address-taken range).

### Where invariants live

Invariants and measures are written on the Lean side and refer to labels. The
text of the structured form carries only the labels.

```lean
nocompiler_auto sum
  loop_inv $next (fun u => ∃ k, ...) measure (fun u => ...)
```

No addresses appear, so relinking does not change the text of a proof.

### Tools

- `nocompiler asm`: from the text to a relocatable object and its metadata.
  An encoder that neither optimises nor selects; not trusted.
- `nocompiler disasm`: the inverse. clang's output becomes the same text.
- Round trip: for every function at L1 or above, `asm(disasm(x))` equals x
  byte for byte (tested).

## Theorems from the checks

Proved once for all programs; per function, only the kernel's evaluation of
the checker is needed.

| Theorem | Level | Content | What disappears from per-function proofs |
| --- | --- | --- | --- |
| T1 structure | L1 | Reachability shown in the structured semantics implies the machine's `Exec` | tracking the pc, staying in the code region, instruction fetch, computing callee addresses |
| T2 slots | L2 | Slots behave as variables: an `ld` reads the last `sd`, unaffected by stores and calls in between | tracking frame reads and writes |
| T3 ABI | L2 | At returns and tail calls, `sp`, `gp`, `tp`, `s0` to `s11` hold their entry values and the return goes to the entry `ra` | `Preserved` and `Same` |
| T4 stack bound | L2 | Every stack access is within `depth f` bytes below the entry `sp`; `depth f` is the function's frame plus the maximum over its callees | writing `Spec.stack` by hand; stack permission obligations |
| T5 verification conditions | L1 | If the verification conditions computed on the structured form hold, the spec holds | building per-instruction symbolic execution into proof terms |

### The structured semantics

An execution defined along the statements of the structured form. It differs
from the machine semantics in that:

- **There is no pc.** A branch is the outcome "leave to label `$l`"; a call is
  "go to a state the spec of symbol `f` allows".
- **At L2, slots are part of the state.** `ld r, k(sp)` and `sd r, k(sp)` read
  and write slot variables and do not touch memory.
- **It gets stuck on accesses without permission,** like today's `Step`.
  Loads and stores not based on `sp` must lie in a region of the spec or in
  the function's own address-taken ranges.

T1 needs one direction only (from the structured semantics to the machine):

```lean
theorem Struct.sound (h : f.check L = true) :
    SExec f L P Q s → Exec L.code P.withStack (L.dom f) Q s
```

`L` is the placement (an assignment of addresses to symbols).

### What "free inside a proof" means

T2 and T3 rely on other stores not clobbering slots. That is guaranteed by:

- the structured semantics getting stuck on a store without permission;
- the stack separation premise: the regions a spec lists do not overlap the
  `depth f` bytes below the entry `sp`.

So T2 and T3 hold unconditionally for a function whose proof went through in
the structured semantics; nothing is claimed for functions without a proof.
Across calls likewise: a callee can write only the regions its caller passed
and its own stack below the current `sp`. The caller's slots are in neither,
so the existing `Verified.frame` shows they do not change.

### T5 in two stages

First, rebuild the current symbolic-execution tactic (`nocompiler_auto`) on
T1 to T4, with calls, syscalls and frames. Then move to computing the
verification conditions as a Lean function (reflective VC generation, Vale
style).

## Specs and proofs

The shape of `Spec` stays almost as it is. Three things change: the stack
moves to the checker side, `Verified` takes the placement as an argument, and
cut points may also be block ends. Termination stays part of every claim.

### The stack leaves the spec

- `Spec.stack` is not used for L2 functions; T4's `depth f` replaces it. L0
  and L1 functions keep it.
- `Entry` gains two conditions: stack separation (the spec's regions do not
  overlap the `depth f` bytes below the entry `sp`) and the stack not wrapping
  around address 0.
- At a call, both are discharged arithmetically (the regions passed are ones
  received or the function's own address-taken ranges, neither below the
  current `sp`).

### `Verified` takes the placement

The unit of proof is a *module*: relocatable functions (words and
relocations) and data. A placement `L` assigns addresses to symbols, and
`M.link L` computes the resulting image.

```lean
def Verified (M : Module) (f : Sym) (spec : Spec α) : Prop :=
  ∀ L, M.Ok L → ∀ a s,
    Entry (L.dom f) (L.addr f) s → spec.pre a s →
    Exec (M.link L).code (spec.perm a s) (L.dom f) (spec.Done a s) s
```

`M.Ok L`: functions are 4-byte aligned and disjoint; callees and data are
within `auipc` reach (about 2 GiB either way). The claim is about the
machine's `Exec`, so the adequacy theorems apply to each placement as they
are. A proof's body never looks at `L`; T1 deals with address computation
once.

### Relocation

Switch to `-mcmodel=medany`, so every address in code is pc-relative.

| Relocation | Where | Seen with clang 18.1.3 |
| --- | --- | --- |
| `R_RISCV_CALL_PLT` | the 2 words of `call` and `tail` | yes |
| `R_RISCV_PCREL_HI20` | `auipc` of a data address | yes, with `medany` |
| `R_RISCV_PCREL_LO12_I` | immediates of `addi` and loads | yes, with `medany` |
| `R_RISCV_PCREL_LO12_S` | immediates of stores | yes, with `medany` |

With the default `medlow`, data addresses are embedded absolutely in
`lui`/`addi` (`R_RISCV_HI20`/`R_RISCV_LO12_I`). Branches within a function are
resolved at assembly and leave no relocations.

Audit: Lean reads the symbol table of the final ELF to build a placement `L₀`,
evaluates `M.link L₀`, and checks that it equals the ELF's `.text` and data
byte for byte. If it does, `Verified` at `L₀` is a theorem about that ELF's
bytes. A wrong `link` only makes the audit fail, so `link` is not trusted.

### Cut points

- **Loop heads:** an invariant and a measure are required.
- **Block ends:** an assertion may be placed. Paths join there (which stops
  the multiplication of paths).

The logic already accepts arbitrary cut points; only the front end, which
rejects anything but loop heads, changes.

## Modules, linking, environment model

```lean
-- T6 composition: adding modules keeps the existing theorems
theorem Verified.mono : Verified M f spec → Verified (M ++ M') f spec
```

- **Export:** a module exports a spec and a `Verified` theorem per function.
- **Calls:** a caller gets the callee's theorem in the combined module by T6
  and uses it through `Verified.call`, never looking at the callee's code.
- **Call graph:** acyclic in v1; recursion later.
- **Ledger:** a library entry is the hash of the relocatable function, its
  spec, the theorem's name, its level and `depth`. The hash does not depend
  on the placement.

### Environment model (deferred from v1; decision 6)

Make the environment an argument of the theorems: `Step`/`Exec` take an
environment `E` (a relation per syscall number), with today's four provided
as `Env.linux0`. Unverified external functions likewise as assumed specs
listed in the theorem. A model of the heap itself is out of scope.

## Metadata v2

`.nocompiler.struct` goes to version 2: positions become function-relative,
labels and the frame partition are added. As in version 1 it is not loaded
and no proof depends on it.

| Item | Version 1 | Version 2 |
| --- | --- | --- |
| Function identity | absolute entry address | symbol (by name; see metadata.md) |
| Node range | absolute `start` and `end` | offsets from the function's start |
| Node label | none | a name (optional; `disasm` invents the rest) |
| Callees | entry addresses | symbols |
| Frame | size only | size, the slots (offset, save or spill, which register for a save), the address-taken ranges (offset and length) |
| Level and `depth` | none | per function |

M1 is extended to: the recorded tree, partition, callees and level agree with
the code. `nocompiler export` writes them as Lean definitions and the kernel
evaluates the checker on them. An extension area for proof hints is reserved
(contents undecided). The encoding is in [metadata.md](metadata.md).

## Effect on the trusted base

Nothing is added. The structured semantics, the R4 to R6 checker and the VC
generator are not trusted, because T1 to T5 connect them to the machine's
`Exec`. `M.link` is not trusted, because the audit matches it with the ELF
byte for byte. `nocompiler asm` and metadata v2 are not trusted. Three
definitions one reads to check change: `Verified` (quantified over the
placement `L`), `Entry` (two more conditions), and the environment
(deferred). The known gaps in `trust.md` do not move.

## Not done

Load-time enforcement, a new instruction encoding, x86/Arm, a verified
compiler (exists elsewhere). Also: data confinement, safety claimed from the
checks alone, value typing as a rule, relaxing R3, another IR language or
lifting to Lean functions. Later: a safety predicate for non-terminating
programs, jump tables, typed indirect calls, recursion, the heap, an LLVM
target feature, Rust, L2 for more than eight arguments.

## Acceptance criteria

| # | Item | Now | Passes when |
| --- | --- | --- | --- |
| 1 | the proof of `sum2` | `Sum2.lean`, 254 lines by hand | about the size of `sum`'s automated proof (12 lines), writing no register preservation, frame or stack separation |
| 2 | functions that make syscalls | `Hello.lean`, 275 lines by hand | `write_all` and `hello` go through `nocompiler_auto` |
| 3 | relocation | proofs fixed to addresses | the same object, linked two ways (different base, different function order), passes the audit both times with the proof text unchanged |
| 4 | corpus conformance | R1 to R5 judged in Rust | every function gets a level, failures name the rule, functions with frames reach L2 |
| 5 | round trip | none | `asm(disasm(x))` equals x for every function at L1 or above |
| 6 | negative controls | proofs fail on mutated binaries | also: remove a restore, write a save slot mid-function, take a slot's address, break a call's distance; each fails the checker or the audit |
| 7 | checking cost | COBS (55 instructions): about 28 s, about 1.7 GB | time and memory measured at 55, 160 and 500 instructions, roughly linear in the instruction count |
| 8 | the demo's A/B | no difference on leaf functions (95 lines vs 95) | on functions with calls and frames, the nocompiler side's proof is shorter than the plain rv64gc side's |
| 9 | LLM-written code | PTX only (102 of 104) | 50 or more tasks in the RV64 structured form; proved / refuted / unknown counts and token counts recorded, and compared with going through clang |

If 8 does not pass, we do not claim "easier to prove".

## Order of implementation

1. R4 to R6 in Lean. Metadata v2, T3, T4. Criteria 4 and 6.
2. The structured semantics, T1, T2. `nocompiler_auto` extended to calls,
   syscalls and frames. Criteria 1, 2 and 8.
3. Relocation: `medany`, modules, `Verified` with a placement, the audit, T6.
   Criterion 3.
4. The text format and `asm`: label references, the round-trip test, the LLM
   benchmark. Criteria 5 and 9.
5. Finishing: block-end assertions, reflective VC generation, environment
   parametrisation. Criterion 7.

## Decisions on the open items (by the user, Nov 20)

1. Placement: v1 opens Version 1; jump tables, indirect calls, recursion,
   LLVM, Rust and mmap come after it.
2. Switch to `medany` (rebuild the committed example ELFs and their proofs).
3. L2 covers up to 8 arguments, passed in registers.
4. Invariants live on the Lean side only; the text carries only labels.
5. Range lengths: from clang's `-g` debug information (DWARF variable sizes);
   without it, a conservative heuristic (the gap up to the next slot).
   Report which was used.
6. Environment parametrisation is deferred (outside v1).
