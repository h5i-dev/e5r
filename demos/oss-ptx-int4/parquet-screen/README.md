# Parquet pivot screen: incomplete build, no candidate claim

After FP4 missed its performance/proof gates, the next screen pinned cuDF to
[`d71b3b743ca6fc9d8d4b1718d845eec4bc63dee6`](https://github.com/rapidsai/cudf/tree/d71b3b743ca6fc9d8d4b1718d845eec4bc63dee6),
Apache-2.0. `evidence/sources.tar.gz` retains the selected original source and
license; `result.json` records file hashes and attempted commands.

The real normal kernel is `decode_page_data_generic` in
`cpp/src/io/parquet/decode_fixed.cu`, with the host's actual template dispatch
at the bottom of that file. Its RLE/dictionary/definition-level machinery is
in `rle_stream.cuh`; this is practical integer bit-packed decoding.

The source already has the proposed important techniques: `page_data.cuh`
uses `__funnelshift_r` to assemble words across boundaries, and the chunked
literal decoder in `rle_stream.cuh` uses a guarded unaligned 32-bit load with
per-byte tail fallback. The normal dispatch, boundaries and specialized
variants cannot fairly be replaced by a deliberately naive byte decoder.
Source inspection does not prove that every compiler route is optimal.

Two actual build attempts were retained. Normal Release CMake configuration
fails because this pin requires CMake >=4.0 while the host has 3.22.2. A direct
unchanged-TU compile, initially missing RMM entirely, still fails after adding
RMM's real include tree: `rmm/version_config.hpp` is generated by its build.
That current RMM pin also requires CCCL >=3.3, newer than the toolkit's CCCL
3.2. These attempts do not reproduce the complete normal dependency graph or
its final compile flags. No headers were stubbed and no kernel body was
simplified to obtain a weaker baseline.

This entry is an incomplete compiler screen. There is no frozen generated PTX,
direct edit, GPU timing, or accepted proof. It is not counted as a completed
optimization/proof attempt or evidence that cuDF cannot be optimized. A full
future attempt needs a compatible RAPIDS/CMake/CCCL/RMM build environment;
none of the FP4 measurements is attributed to this kernel.

`screen.py` replays the two attempted commands against the existing pinned
scratch clones. It is CPU-only and changes no upstream files. Source was
read for this screen; no reverse-engineering tool implementation was consulted.
